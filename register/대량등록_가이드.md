# Wix 등 외부 사이트 개체 대량 등록 가이드

Wix 등에서 운영되던 기존 종족의 개체들을 종족연구소 DB로 대량 이관할 때 쓰는 표준 절차. 테일스 종족(species id=169, 0000~1108, 총 1109개체, 2026-08-08 완료)에서 처음 확립되고 검증됨. 다음 종족부터 이 절차를 그대로 재사용한다.

## 전체 흐름

1. 원문 수집 (WebFetch)
2. 정제 스크립트로 DB 등록용 JSON 생성
3. 뽀 검수 → 누락/오류 보정 (반복)
4. 이미지 리사이즈 (2000×2000px 제한 대응)
5. `pages/bulk-import.html`의 "JSON 일괄 등록" 모드로 실제 DB 등록

---

## 1. 원문 수집

### 사이트 구조 확인
- Wix 사이트는 대부분 **완전 클라이언트 렌더링**이라 `curl`로는 본문이 안 잡힌다(빈 HTML만 받아짐). 반드시 **WebFetch 도구**를 써야 한다.
- `{사이트}/sitemap.xml` → `blog-posts-sitemap.xml`에서 전체 게시물 URL 목록을 얻을 수 있다.

### 번호-URL 매칭 시 주의 (중요)
URL 슬러그에 박힌 번호나 이름 텍스트가 **실제 개체 번호·내용과 다른 경우가 왕왕 있다.**
- 예: URL은 "100-야채호빵의-테일스"인데 실제 페이지 내용은 "100.블랙커피의 테일스"이고, "101-블랙커피의-테일스" URL이 실제로는 101번 "야채호빵" 내용인 경우 (인접한 두 게시물의 슬러그 텍스트가 서로 뒤바뀜)
- 예: URL 슬러그 이름이 아예 비어있거나("836.의 테일스") 오래된 이름을 담고 있는 경우

**대응**: 뽀가 미리 정리해둔 전체 번호.이름 목록(`tails_name.txt` 같은 파일, 사이트의 "최근 게시물"/개체 리스트 위젯에서 추출)을 매칭 기준으로 삼되, **최종적으로는 실제 페이지에 적힌 번호와 등록하려는 char_number가 일치하는지 반드시 대조 검증**한다. `clean_tails_generic.js`가 이 검증을 자동으로 수행한다(아래 참고).

### WebFetch 프롬프트
원문을 요약 없이 그대로 뽑아내려면 아래처럼 강하게 지시해야 한다. 순한 프롬프트는 WebFetch가 자체적으로 요약/의역해버리는 경우가 잦다(특히 콘텐츠가 특이한 페이지일수록 심함).

```
Do NOT summarize or paraphrase anything. Do NOT write your own sentences. Copy-paste the raw
visible text of the page EXACTLY as it appears, byte for byte, in the original Korean,
preserving every comma and missing space exactly as shown. Start from the title (e.g.
"NNN.XXX의 테일스") and stop right after the "최근 게시물" list. If you cannot access the
full raw text, say "CANNOT ACCESS FULL TEXT" instead of making anything up.
```

그래도 의역되어 돌아오는 경우가 있다 — 특징: `[능력: ]` 대괄호가 비거나, 문장이 "~습니다"체로 바뀌거나, 영어로 요약되어 옴. 이런 결과는 버리고 재시도한다.

### 대량 병렬 크롤링 시 주의사항
- **동시 실행 서브에이전트는 2~3개로 제한**할 것. 한꺼번에 많이 돌리면 Claude API 세션 사용량 한도에 반복적으로 걸리며, 리셋 시간이 계속 밀리는 현상이 생긴다. 하나 끝날 때마다 다음 배치를 투입하는 방식이 결과적으로 더 빠르고 안정적이다.
- 서브에이전트가 임시 폴더를 쓸 땐 **배치 전용 이름**을 쓰게 할 것(예: `_tmp_0801_0900`). 이름이 겹치면 다른 배치의 임시 데이터가 지워지는 사고가 난다.
- 같은 URL에 대한 재시도는 최대 1회로 제한하고, 그래도 실패하면 즉시 `needs_review` 목록으로 넘기고 다음으로 진행한다(무한 재시도 금지).
- **원문을 raw JSON에 반드시 저장한 뒤 정제 스크립트로 clean JSON을 생성하는 파이프라인을 지킬 것.** 서브에이전트가 편의상 clean JSON에 직접 손으로 써넣고 raw 저장을 건너뛰는 경우가 있었는데, 이러면 나중에 정제 스크립트를 다시 돌릴 때(버그 수정 등으로 재실행 시) 그 항목이 통째로 사라진다. raw에 없는데 clean에만 있는 항목이 없는지 주기적으로 대조 확인한다.

## 2. 정제 스크립트 (`register/tails/clean_tails_generic.js`)

사용법:
```
node clean_tails_generic.js <raw.json> <out_clean.json> <out_report.json> [rangeStart] [rangeEnd]
```

raw.json 형식: `[{ "number": "0101", "url": "...", "text": "<WebFetch 원문 그대로>" }, ...]`

정규식으로 아래를 추출해서 DB 등록용 스키마로 변환한다:
- 제목 줄에서 번호+이름 (마크다운 `#`/`**` 잔재, WebFetch가 붙이는 "- Full Body Text" 같은 안내문구 자동 제거)
- `(파트너: X )` / `(계약자: X)` / `(전언자: X)` 등 소유주 호칭 변형 대응
- `주식:X/Y` + `[능력:...]` 블록 (대괄호가 비었거나 순서가 뒤바뀐 변형, 닫는 대괄호 자체가 원문에 없는 경우까지 fallback 처리)
- description (문단들을 공백 없이 이어붙임 — 원본 사이트의 raw 텍스트 관행과 동일하게)
- **페이지 제목에 실제 적힌 번호 vs 지정한 char_number 불일치 검증** (다른 개체 내용이 잘못 들어간 경우를 잡아냄, error로 표시)

새로운 원문 변형 포맷을 만나면(예: 새로운 소유주 호칭, 새로운 대괄호 표기 오류) 이 스크립트에 패턴을 하나씩 추가하면 된다 — 실제로 이번 작업 중 여러 번 그렇게 대응했다.

## 3. 뽀 검수 루프

100단위로 배치를 나눠서(`tails_XXXX_YYYY_clean.json`) 뽀가 하나씩 확인하며 진행하는 방식이 잘 작동했다:
- 빠진 번호 물어보면 → raw/clean 대조해서 결번 목록 보고
- 원문이 의역된 게 의심되면 → 뽀가 직접 원문을 복사해서 전달 → raw+clean 둘 다 갱신
- 미완성 placeholder 개체(이름/주식/능력 등이 실제로 비어있는 경우)는 이름은 원문 그대로, 나머지는 null로 등록
- 사이트에 게시물 자체가 없는 경우(404) → 결번으로 확정, 등록하지 않음
- 번호-URL 매칭이 꼬였던 특이 케이스들은 원래 번호의 배치 파일로 병합 — 별도 파일로 계속 분리해두지 말 것(관리 포인트가 늘어남)

`needs_review` 배열(`{char_number, url, reason}`)로 불확실한 항목을 추적하다가 해결되면 그때그때 지운다.

## 4. 이미지 리사이즈

사이트 업로드 제한: **최대 2000×2000px**.

PowerShell + .NET `System.Drawing`으로 리사이즈(별도 라이브러리 설치 불필요):
```powershell
Add-Type -AssemblyName System.Drawing
# Image.FromFile → 비율 계산 → Bitmap + Graphics.DrawImage(HighQualityBicubic) → Save
```

**주의**: 이렇게 저장하면 PNG에 `sRGB`/`gAMA`/`pHYs` 색상 프로파일 청크가 자동으로 붙는데, 사이트 업로드 검증이 이걸 "이미지 파일을 읽을 수 없습니다 / 색상 프로파일을 확인해주세요" 오류로 거부한다. 리사이즈 후 반드시 `register/tails/strip_png_color_chunks.js`로 해당 청크를 제거해야 한다(픽셀 데이터는 그대로, 메타데이터만 제거 — 화질 손상 없음).

```
node strip_png_color_chunks.js <파일1> <파일2> ...
```
